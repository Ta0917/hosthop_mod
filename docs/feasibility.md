## プレイヤーUUIDの調査

提供された古いワールドのコピーと、別途コピーしたユーザーキャッシュを読み取り専用で比較した。キャッシュ6件には同じ名前で異なるUUIDがあるグループが2組あり、各組に名前から計算したオフラインUUIDと一致するIDと、別のIDの両方のプレイヤーデータが存在する。指定版のMinecraftソースでは、統合サーバーの認証が失敗または利用不能の場合にオフラインUUIDを生成する経路が確認できた。ただし、今回の重複の発生原因や、別のIDが現在の正規アカウントに対応することをこの観察だけでは断定できない。

ユーザー指示に基づき、両組の保存データ・統計・進捗を比較し、プレイ時間、完了進捗、統計件数がいずれも明確に多い側を、このコピーの採用対象として選択した。各組の4件について、NBT内のUUIDとファイル名が一致した。個別の名前・UUID・指標はGit管理対象外の `test-data/identity-metadata/selected-profiles-v3.json` に保存し、対象ワールドとキャッシュのハッシュも記録した。両方のデータはそのまま保全し、移動・統合・削除・UUID書き換えはしていない。これは古いコピーだけの判断であり、後日提供される本番ワールドや実アカウントのUUIDとの対応は再確認する。

コピーした過去ログには、認証サーバー利用不能の警告に続いて該当する両プレイヤーが参加した記録があり、オフラインUUIDを生む経路と整合する。ただしログだけで各ファイルのすべての来歴を確定できない。選択した2件のMojang公開プロフィール照会は、当初UUIDの外部送信として自動承認審査に拒否された。その後、ユーザーが2件のUUIDをMojang公式サービスへ送ることを明示的に許可し、2件とも公開プロフィールの名前とUUIDが一致した。これは本人のログインやアカウント所有の認証ではない。

読み取り専用の `poc/uuid_audit.py` は集計だけを表示し、`poc/player_progress.py` は任意のコピーから個別レポートを新規作成する。後者は `poc/requirements-audit.txt` のNBTライブラリが必要で、NBT内のUUIDがファイル名と一致しない場合、時間・進捗・統計の差が不十分な場合や必要データが欠ける場合は自動選択しない。インベントリーや経験値だけを優劣の決定基準にしない。

## 安全性の設計候補

Cloudflare Workers Free + D1を制御面、Google Driveをデータ面とする案を候補にする。[D1 Free](https://developers.cloudflare.com/d1/platform/pricing/)は1日500万行読取・10万行書込で、超過時はクエリが失敗する。無料枠に収まること、課金設定、認証、Drive共有・所有者離脱、アップロード性能は未確認。Googleの[デスクトップOAuth](https://developers.google.com/identity/protocols/oauth2/native-app)とPKCEを検討するが、利用者間の認証と保管先の権限設計は未決定。無料枠超過や障害時は停止する設計とし、課金を前提にしない。

制御面の信頼できる時刻と単一原子的な条件付き更新を使い、所有者・期限・単調増加するepoch・確定世代を管理する。新規ホストは有効リース取得と最新確定世代の検証後にのみ起動する。旧epochや期限切れ、想定外の世代からの確定を拒否する。リース更新失敗時は安全余裕をもってゲーム処理と外部公開を停止する必要があり、旧ホストの停止を確実に確認できない場合、分断中の二重プレイを防ぐ設計は未完成。クライアントの時計や協調動作だけを安全性の根拠にしない。悪意あるローカルホストによる改変は防げない。

ローカルD1候補は、期限切れだけを理由とする自動引き継ぎを拒否するよう変更した。旧ホストの正常解放または安全性を確認した別途の復旧がなければ、新しい取得を保留する。これは分断時の安全性を優先して可用性を下げる設計で、異常終了後の復旧手段は未実装。SQLの解放操作だけでは実際にサーバーが停止したことを証明できず、認証と停止確認が必要。従来の `poc/lease_model.py` と `poc/local_catalog.py` はこの新しい条件を持たない別の初期実験で、本番利用しない。

D1候補では、安全判断に古い読み取り結果を使用しないことが必要。[Cloudflareの説明](https://developers.cloudflare.com/d1/best-practices/read-replication/)では読み取りレプリカは非同期で遅延し得るため、リースと最新世代の判断をレプリカの任意の読み取りに依存させない。また[batchの複数文は1トランザクション](https://developers.cloudflare.com/d1/observability/find-expensive-queries/)だが、ローカルSQLiteの対話的な `BEGIN IMMEDIATE` をそのまま移植できると決めつけず、D1向けのSQL設計・実環境検証が必要。

確定手順の候補は、サーバー停止または一貫性が実証された保存境界で全ワールドデータをスナップショット化し、変更不能な新規オブジェクトとしてアップロード、長さと暗号学的ハッシュを再検証し、その後にリースと旧世代を条件に確定ポインターを原子的更新すること。失敗時は旧世代を残す。アップロード済みでも確定前のデータは最新版として扱わない。保存中コピーの一貫性、MOD固有データ、復元、容量の事前確認、バックアップ削除の確認は未実装。

## PoCと限界

`poc/lease_model.py` はSQLiteの条件付き更新をローカルで試すだけのモデル。16件の同時取得、期限切れの旧ホストによる更新、古い世代の確定をテストした。呼び出し側から時刻を渡すため実サービスで安全ではなく、認証、アップロード、整合性検証、障害復旧、ゲームの停止は実装していない。D1の実環境でのトランザクション、整合性、タイムアウトや再試行も未検証。

`poc/snapshot_manifest.py` は停止済みコピーの全ファイルについてサイズとSHA-256を記録し、欠落・変更・追加を検出するローカル検証。提供ワールドのコピーに対し作成後の再検証が一致した。ハッシュは内容の正しさやセーブの一貫性、ゲームからの復元可能性を証明しない。ライブワールドのスナップショット作成・クラウド同期にも対応していない。

`poc/offline_backup.py` は、停止済みのコピーに対するZIP保存・全ファイルのサイズとSHA-256の検証・新規フォルダーへの復元を試すコード。既存バックアップや復元先の上書きを拒否し、不正なパスや破損ファイルを検出する。提供ワールドのコピーで213ファイルを保存・復元し、全ファイルのハッシュ一覧が一致した（元コピー279,049,002バイト、ZIP 244,477,103バイト、保存・復元・再照合の合計12.7秒、このPC上の1回のみ）。ゲームでの復元後起動は未確認。保存中の失敗時に不完全なZIPが残る場合があり、復元途中の失敗時も不完全なフォルダーが残るため、それらを正常なバックアップや復元データとして扱わない。空ディレクトリー・ファイルの時刻や権限は保存せず、動作中ワールドの整合性・容量管理・世代管理・クラウド同期・自動バックアップは未実装。本番用バックアップ機能ではない。

`poc/local_catalog.py` は上記のZIPとSQLiteの実験モデルを接続する。ローカルの一時ファイルにコピー後、ZIP内容とSHA-256を検証し、同じ内容を示すオブジェクト名で既存ファイルを上書きせずに公開する。その後、リース・epoch・確定世代を条件とした更新を試す。破損・不完全なZIP、期限切れホスト、同時確定、保存物の破損、同一オブジェクトの同時公開をテストした。提供ワールドのコピーから作成したZIPでも1世代を確定・213ファイルを復元し、ハッシュ一覧の一致を確認した。これは単一PC上のPoCで、呼び出し側が時刻を指定でき、検証後のファイル変更も原理的には防げない。プロセス強制終了・停電時の永続性、クラウドストレージの原子性、認証、悪意あるホスト、保持世代管理、複数PC間の排他と分断時のプレイ停止は保証していない。

回線切り替えによるホスト停止後、停止したテストセッションの381ファイルをコピーして照合し、期限切れのテスト用リース解除後にそのコピーを新世代として保存した。保存したアーカイブはDriveから再取得して完全一致を確認した。この操作は停止とデータを個別確認した手動復旧で、通常の自動復旧には対応していない。

利用者の方針により、信頼された招待メンバーの間でOP・一般の権限分離を行う要件は不要になった。共有ワールドの同期やデータ保護は引き続き必要。

ホスト起動時、クラウド管理情報の最新版とサイズ・SHA-256が一致する過去セッションのアーカイブがローカルにあれば、それを検証して再利用する。ローカル模擬クラウドの統合テストで、再ダウンロードせず最新版が復元されることを確認した。別ホストが更新した場合など、一致するファイルがなければ従来どおり全体を取得する。保存時の全体アップロードやMinecraft終了後の転送にはまだ対応していない。
